## Read-only checker

`scripts/check-hosted-access.mjs` reads the ignored files in memory and prints check names/statuses only. It sends GET requests, creates no account/object/run/schedule, and never changes hosted settings. Its detailed report defaults to ignored `private/stage-1-hosted-check.json`, mode 600. It does not output keys, user emails, raw capture bodies, signed URLs or passwords.

```sh
node scripts/check-hosted-access.mjs
node scripts/check-hosted-access.mjs --app-url=https://YOUR-ACTUAL-SITE --netlify-site-id=YOUR-ACTUAL-ID --trigger-run-id=run_ACTUAL --expected-commit=ACTUAL_COMMIT_SHA
```

Optional audit-only values may be entered directly into ignored `.env.hosted-check.local`: `NETLIFY_AUTH_TOKEN`, `TRIGGER_PRODUCTION_READ_KEY`, `HOSTED_CHECK_OWNER_ACCESS_TOKEN`, and `HOSTED_CHECK_OTHER_ACCESS_TOKEN`. Use the narrowest existing provider API access suitable for reads; do not put these values into application templates. User access tokens must come from existing independently authenticated accounts, and are optional. Without them, owner/other-user HTTP checks stay setup-needed. The checker never requests a password or signs anyone in. Do not place credentials on its command line.

The checker reads schema/count/provenance with the service secret, tests anonymous reads with the publishable key, checks Auth signup settings and private bucket/object access, and optionally verifies independently supplied user JWT identities before their RLS/download checks. It can inspect a ready Netlify deploy and a completed production Trigger run. It does not prove catalog policy definitions, complete hosted UI acceptance, backup/restore, retention races or a laptop-off interval. It always leaves overall acceptance false for those explicit gates.

Exit 1 means a check failed; exit 2 means setup/evidence remains incomplete. This version deliberately retains the manual catalog/UI/offline gates, so even successful implemented read checks return exit 2 until a separate acceptance record closes them. In its initial execution with empty local credentials and no target production files, it made **zero network requests**, returned exit 2, and recorded setup-needed rather than an empty-success result. Node syntax checking passed. That run is not a hosted integration test.

## Laptop-off evidence

Record an explicit user-confirmed off interval in UTC, including start/end and how “off” was established. Closing a terminal, stopping the dev worker, sleeping a laptop or observing cloud runs while this agent is active does not by itself establish a powered-off interval. Do not claim the laptop was off without that confirmation or trusted device evidence.

Before the interval, capture the production worker version/schedule, last committed source-run IDs, existing normalized counts and deployed app commit. Ensure both adapters will become due within the chosen interval; Music's six-hour cadence means a short interval may prove only central collection. Stop local collection/dev dispatch. Do not alter production due times merely to manufacture offline proof.

After the interval, read provider-side run history and database commits. Acceptance requires a Production scheduled cloud run started and completed inside the confirmed interval, at least one real due-source collection committed in that run, exact source-run/capture correlation, and the resulting real facts visible after owner login. To claim both adapters continued offline, collect this evidence for each adapter during its due window. If the cloud API only exposes timestamps and the worker does not preserve exact SQL run IDs, mark correlation incomplete; overlapping timestamps are supporting evidence, not a durable identity link.

Keep the private evidence manifest with off-window provenance, Trigger run IDs/version/environment/schedule, exact SQL source-run IDs, source windows/counts/hashes, post-window owner-visible facts, and observed provider charges. Exclude credentials and full private content. No “newly announced event” is required: a successful fresh fetch of unchanged source data plus a new durable observation is valid, while facts/versions remain deduplicated.

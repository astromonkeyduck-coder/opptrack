# Local recovery verification

Run `node scripts/test-recovery-restore.mjs` from the repository root. It reads the installed PGlite package, the test-only Auth/Storage SQL shell, and every migration. It reads no dotenv files or hosted credentials, makes no HTTP requests, and does not invoke the calendar executor. It creates only synthetic facts and local object bodies. No service is provisioned or upgraded.

The drill builds one source-backed program, one timed occurrence, one separate date-only application milestone, field evidence, a saved review decision, and a private intake with two locally generated PNG slides. The source capture is a third separate object. The worker and owner actions use the actual migrated SQL RPCs.

It exports the complete PGlite data directory and separately copies all three object bodies with byte counts and SHA-256 hashes. The package and manifest stay under an ignored `private/recovery-drill-*` directory, with private artifact modes. A fresh corruption test rejects an altered database archive, an altered object and a missing object before restore. These checks detect accidental corruption relative to the local manifest; the manifest is not an authenticated offsite backup.

The original synthetic database is deliberately changed, its review decision is removed, and its original object files are deleted. That database is then closed. The valid package initializes a separate local database directory, and the object bodies are restored into a separate directory. Every application/private/Auth-shell/Storage-shell table's row count and digest, ownership policies, RLS flags, views and function grants must match the snapshot. The checks then prove owner visibility, anonymous/nonowner isolation, intact ordered media, preserved stable IDs/decisions, deduplicated recollection, intake idempotency, and continued decision sequence allocation. Closing and reopening the restored database verifies its local persistence. Both calendar tables stay empty.

The command writes sanitized results to `reports/stage-1-local-recovery.json`. Its timings describe this small local fixture, not production recovery guarantees. Actual private captures, Google credentials and approved calendar commands are excluded from this drill.

This closes only the **local synthetic restore** check. PGlite's archive is a PGlite data-directory snapshot, not a Supabase logical dump or a managed hosted backup. PGlite documents the [dump/load data-directory route](https://pglite.dev/docs/api#dumpdatadir). The SQL Auth/Storage shell does not reproduce hosted Auth, JWT verification, Storage HTTP or managed-service recovery.

A production recovery gate still needs an authorized real backup and an isolated destination with no schedulers or writers, complete restoration of database roles/schema/data/migration history, independently restored Storage bodies and hash coverage, signed-JWT owner/nonowner/anonymous checks, and confirmation of credential-key/reconnection handling without replaying calendar commands. [Supabase database backups exclude Storage object bodies](https://supabase.com/docs/guides/platform/backups); use its separate [database and Storage restoration guidance](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore). No production retention deletion, backup restoration, new paid environment or provider upgrade is performed by this command.
